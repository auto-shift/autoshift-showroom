= Start the long-running builds
include::partial$_attributes.adoc[]
:navtitle: Module 3: Start the long-running builds

Module 2 ended with `local-cluster` assigned to the `hub` clusterset and the full label flow running. Everything you have done so far completes in seconds.

Two things in this lab do not. Building a registry on the lab cluster takes around 40 minutes, and provisioning an OpenShift cluster on Amazon Web Services (AWS) takes around 40 more. Run them one after another and you spend most of the workshop watching progress indicators.

You do not have to. Both are declarative: you write labels and values files, and the machinery converges on its own. So declare both now, then spend the next several modules doing useful work while they build. Module 10 returns to collect the results.

That is not a scheduling trick. It is the argument for declarative fleet management stated as a workflow. You describe the end state, the controllers reconcile toward it, and your attention is free in the meantime. A fleet operator does not sit and watch 200 clusters converge.

[WARNING]
====
*This module starts work that costs real resources.*

*The registry.* OpenShift Data Foundation (ODF) Multi-Cloud Gateway (MCG) in standalone mode plus Red Hat Quay run on the lab cluster and need genuine compute headroom. If your cluster cannot take it, skip Exercise 1 and use the fallback path documented in Module 8.

*The cluster.* Hive provisions a real OpenShift cluster on AWS: Elastic Compute Cloud (EC2) instances, a Virtual Private Cloud (VPC), NAT gateways, Elastic IPs, and Route 53 records. The lab environment supplies a sandbox AWS account, so you are not spending your own money, but the resources are real.

*Teardown is mandatory.* Module 10 tears the cluster down. It is not optional. If you skip it, billing continues.
====

== Learning objectives

By the end of this module, you'll be able to:

* Declare a container registry and an entire OpenShift cluster using nothing but labels and values files
* Build the single source secret that cluster-install reads for AWS credentials, SSH keys, and the pull secret
* Explain why enabling Federal Information Processing Standards (FIPS) mode constrains which SSH key algorithm you may use

== Exercise 1: Declare the registry

Module 8 publishes AutoShift to an Open Container Initiative (OCI) registry. It needs a registry to publish to, and AutoShift can install one.

Quay needs object storage. Rather than a full ODF deployment with Ceph and dedicated storage nodes, `odf-multi-cloud-gateway: standalone` brings up NooBaa alone. That is what makes a registry viable on a single lab cluster: the shipped `QuayRegistry` sets `objectstorage: managed: true`, and NooBaa satisfies it.

. Write the hub clusterset file. It declares the registry, and adds the `config:` section Quay needs
before it rolls out.
+
[source,role="execute"]
----
cat > autoshift/values/clustersets/hub-minimal.yaml << 'EOF'
# Minimum Hub Cluster Configuration
hubClusterSets:
  hub:
    config:
      # Quay ships no bootstrap Job, so the registry starts with no users. Module 8 creates the
      # first one through the registry API, and that endpoint is only reachable when these are
      # set BEFORE Quay rolls out.
      quay:
        bootstrap:
          userInitialize: true
          xhrOnly: false
    labels:
      # Required: OpenShift version for image mirroring, cluster installs and upgrades
      openshift-version: '4.22.8'

      # Required: Indicates this is a self-managed hub cluster
      self-managed: 'true'

      ### OpenShift GitOps (REQUIRED)
      gitops: 'true'
      gitops-subscription-name: openshift-gitops-operator
      gitops-disable-default-argocd: 'true'
      gitops-channel: gitops-1.21
      gitops-source: redhat-operators
      gitops-source-namespace: openshift-marketplace

      ### Advanced Cluster Management (AUTOMATIC)
      acm-subscription-name: advanced-cluster-management
      acm-channel: release-2.17
      acm-source: redhat-operators
      acm-source-namespace: openshift-marketplace

      ### OpenShift Data Foundation, NooBaa only
      odf: 'true'
      odf-subscription-name: odf-operator
      odf-channel: stable-4.22
      odf-source: redhat-operators
      odf-source-namespace: openshift-marketplace
      odf-multi-cloud-gateway: standalone

      ### Quay
      quay: 'true'
      quay-subscription-name: quay-operator
      quay-channel: stable-3.18
      quay-source: redhat-operators
      quay-source-namespace: openshift-marketplace

      ### Trust the cluster ingress CA in the ArgoCD repo server.
      ### Module 8 needs this to push charts to the in-cluster registry.
      gitops-cluster-ca-bundle: 'true'
EOF
----

. Apply. This is the same command you have run in every module:
+
[source,role="execute"]
----
helm upgrade --install autoshift ./autoshift \
  -n openshift-gitops \
  -f autoshift/values/global.yaml \
  -f autoshift/values/clustersets/hub-minimal.yaml
----

. Confirm the labels reached `local-cluster`. Run this until both appear:
+
[source,role="execute"]
----
oc get managedcluster local-cluster -o json | grep -E '"autoshift\.io/(odf|quay)"'
----
+
----
            "autoshift.io/odf": "true",
            "autoshift.io/quay": "true",
----

The ODF and Quay policies are now dispatched. They will take around 40 minutes to reach Compliant, and you are not going to wait for them:

[source,role="execute",subs="attributes"]

== How cluster-install works for AWS

The cluster-install policy set is a chain. Each policy depends on the previous one being Compliant before it fires:

[mermaid]
....
flowchart TD
  A["policy-cluster-install-prereqs<br/>Creates cluster namespace,<br/>ClusterImageSet, KlusterletAddonConfig"]
  B["policy-cluster-install-secrets<br/>Copies pull secret and SSH keys<br/>into the cluster namespace"]
  C["policy-cluster-install-aws<br/>Creates Secrets, ClusterDeployment,<br/>MachinePool, ManagedCluster"]
  A --> B --> C
....

All 3 policies read the same `rendered-config` ConfigMap that the `cluster-config-maps` policy built from your values file. Adding a cluster values file is the entire provisioning trigger. No Helm re-rendering and no ArgoCD sync is needed beyond what ArgoCD does automatically.

The policy set reads credentials from a single source secret named `aws-creds` in the `cluster-install-secrets` namespace. That secret holds 5 keys: `aws_access_key_id`, `aws_secret_access_key`, `ssh-privatekey`, `ssh-publickey`, and `pullSecret`. The values file references the same secret 4 separate times through `credentialRef`, `sshPrivateKeyRef`, `sshKeyRef`, and `pullSecretRef`. This shape matches what the ACM console produces, so a secret created by the console works here without modification.

== Exercise 2: Build the source secret

=== SSH key generation

The `aws:` block has a `fips` field. This lab sets it to `false`, and the reason is worth understanding before you generate a key.

When `fips: true`, the OpenShift installer constrains which SSH key algorithms it will accept. Only Rivest-Shamir-Adleman (RSA) and Elliptic Curve Digital Signature Algorithm (ECDSA) are allowed. Ed25519 is not.

There is a second constraint that is easy to miss, and it is why this lab uses `false`. Installing a FIPS cluster requires the *installer host* to be running in FIPS mode as well, and the installer host here is the Hive provision pod on your hub. If the hub is not FIPS-enabled, the provision fails immediately:

----
fips: Forbidden: target cluster is in FIPS mode, enable FIPS mode on the host
----

Hive retries up to `installAttemptsLimit` times and then sets `ProvisionStopped`. Nothing about that message mentions the hub, so it is a confusing failure to hit for the first time on a real cluster.

Check your hub before enabling it:

[source,role="execute"]
----
oc debug node/$(oc get nodes -o jsonpath='{.items[0].metadata.name}') -q -- \
  chroot /host cat /proc/sys/crypto/fips_enabled
----

`0` means the hub is not in FIPS mode, so leave `fips: false`. `1` means you can set `fips: true`, and then the SSH key algorithm matters.

You will generate an ECDSA key regardless. It is correct practice, it costs nothing, and it means the values file works unchanged if you later enable FIPS on a hub that supports it.

This is not an AutoShift constraint. It is the same restriction the OpenShift installation documentation states for FIPS clusters. If you generate an ed25519 key and then provision a FIPS cluster, the install fails during bootstrap validation. The error is not obvious: Hive retries, the provision pod exits, and the failure message does not name the key algorithm directly. Generate the key deliberately rather than reaching for the ed25519 default.

Run this to generate an ECDSA key with a 521-bit curve and no passphrase:

[source,role="execute"]
----
ssh-keygen -t ecdsa -b 521 -N '' -f ~/.ssh/ocp-cluster
----

The flags: `-t ecdsa` selects the algorithm. `-b 521` selects the strongest standard ECDSA curve. `-N ''` sets an empty passphrase, which is required for unattended Hive provisioning. `-f ~/.ssh/ocp-cluster` writes `ocp-cluster` (private key) and `ocp-cluster.pub` (public key) into your `.ssh` directory.

=== Extract the pull secret from the hub

The hub cluster has a valid pull secret stored in `openshift-config`. Extract it rather than downloading a new one from the Red Hat console.

[source,role="execute"]
----
oc extract secret/pull-secret -n openshift-config --to=/tmp --confirm
----

The `--confirm` flag overwrites any existing file at the destination. The command writes `/tmp/.dockerconfigjson`.

=== Create the namespace and the secret

Create the source namespace:

[source,role="execute"]
----
oc create namespace cluster-install-secrets
----

Now create the secret. The AWS credentials come from lab environment attributes, so you do not type any keys. The SSH keys come from the files you just generated.

[source,role="execute",subs="attributes"]
----
oc create secret generic aws-creds \
  -n cluster-install-secrets \
  --from-literal=aws_access_key_id={aws_access_key_id} \
  --from-literal=aws_secret_access_key={aws_secret_access_key} \
  --from-file=ssh-privatekey=$HOME/.ssh/ocp-cluster \
  --from-file=ssh-publickey=$HOME/.ssh/ocp-cluster.pub \
  --from-file=pullSecret=/tmp/.dockerconfigjson
----

Note the `subs="attributes"` on this block. AsciiDoc does not expand attribute references inside delimited code blocks by default. The `subs="attributes"` directive expands `\{aws_access_key_id}` and `\{aws_secret_access_key}` to the values injected by the lab environment, so you never type a key. Shell variables like `$HOME` are unaffected by that substitution and are resolved by your shell at runtime, which is why both can appear in the same command.

=== Verify

Confirm the secret has all 5 keys. `oc describe` prints key names and byte counts and never prints values, which is what you want when checking a secret:

[source,role="execute"]
----
oc describe secret aws-creds -n cluster-install-secrets
----

----
Name:         aws-creds
Namespace:    cluster-install-secrets
Type:         Opaque

Data
====
aws_access_key_id:      20 bytes
aws_secret_access_key:  40 bytes
pullSecret:             2847 bytes
ssh-privatekey:         736 bytes
ssh-publickey:          283 bytes
----

All 5 keys are present, and the byte counts confirm each one carries content. The policy chain can read each of them.

[NOTE]
====
Byte counts on your cluster will differ. What matters is that all 5 keys exist and none is 0 bytes.

Resist the habit of running `oc get secret ... -o yaml` here. That prints the base64 values, which for this secret means your AWS credentials and a private key land in your terminal scrollback. `oc describe` gives you everything you need to verify without that.
====

== Exercise 3: Declare the cluster

=== Enable cluster-install on the hub

The `hub-minimal.yaml` clusterset has no `cluster-install` label. Add it using the same append pattern you used in earlier modules. Open `autoshift/values/clustersets/hub-minimal.yaml` and add the 2 labels under `hubClusterSets.hub.labels`:

[source,yaml]
----
hubClusterSets:
  hub:
    labels:
      # ... existing labels ...
      cluster-install: 'true'
      acm-enable-provisioning: 'true'
----

The `cluster-install: 'true'` label does 2 things: it enables the SiteConfig component on the MultiClusterHub, and it gates the cluster-install policy placement so those policies only run on hubs that carry the label. The `acm-enable-provisioning: 'true'` label enables the provisioning infrastructure ACM needs to track Hive ClusterDeployments.

Apply the change:

[source,role="execute"]
----
helm upgrade autoshift ./autoshift \
  -n openshift-gitops \
  -f autoshift/values/global.yaml \
  -f autoshift/values/clustersets/hub-minimal.yaml
----

=== Create a clusterset for the new cluster to join

A cluster that joins a clusterset inherits that clusterset's labels, and therefore its policies. So the clusterset you assign the spoke to decides what it becomes.

AutoShift ships a full `managed.yaml` profile, but it enables a large set of operators. Build a minimal one instead, the same way `hub-minimal.yaml` is a minimal hub.

Note what is *not* in this file. There is no `self-managed` label. That label is only valid under `hubClusterSets`, where it registers a hub as a self-managed cluster in its own ACM, and the chart rejects it here:

----
'self-managed' is only valid on a hubClusterSets entry
----

You do not need to declare that this is a spoke. AutoShift derives `autoshift.io/cluster-type` (`hub` or `spoke`) from which bucket the clusterset is defined in, so putting it under `managedClusterSets` is the declaration.

Include Node Feature Discovery. You are declaring it here, on a cluster that does not exist yet, and never touching that cluster again. Module 10 checks whether it arrived.

. Read the version your lab cluster is running. Do not copy a version out of this guide: lab environments are provisioned at whatever release is current, and `openshift-version` is the version AutoShift treats as desired, so it should match the fleet you are actually running:
+
[source,role="execute"]
----
OCP_VERSION=$(oc get clusterversion version -o jsonpath='{.status.desired.version}')
echo "$OCP_VERSION"
----

. Create the minimal managed clusterset. The heredoc delimiter is unquoted so `${OCP_VERSION}` is substituted as the file is written:
+
[source,role="execute",subs="attributes"]
----
cat > autoshift/values/clustersets/managed-minimal.yaml << EOF
# Minimal managed (spoke) clusterset for the lab.
# A cluster assigned to this clusterset inherits these labels.
managedClusterSets:
  managed:
    labels:
      openshift-version: '${OCP_VERSION}'

      ### Node Feature Discovery, declared for a cluster that does not exist yet
      node-feature-discovery: 'true'
      node-feature-discovery-subscription-name: nfd
      node-feature-discovery-channel: {nfd_channel}
      node-feature-discovery-source: redhat-operators
      node-feature-discovery-source-namespace: openshift-marketplace
EOF
----

. Confirm the file is valid YAML and reads as you expect:
+
[source,role="execute"]
----
cat autoshift/values/clustersets/managed-minimal.yaml
----

=== Create the cluster values file

Copy the example file and name it after your cluster:

[source,role="execute"]
----
cp autoshift/values/clusters/_example-cluster-install-aws.yaml \
   autoshift/values/clusters/spoke-aws-1.yaml
----

Edit `autoshift/values/clusters/spoke-aws-1.yaml` to the following minimal working configuration. Each field is explained below.

[source,yaml,subs="attributes"]
----
clusters:
  spoke-aws-1:
    config:
      clusterSet: managed

      networking:
        clusterNetwork:
          cidr: 10.128.0.0/14
          hostPrefix: 23
        machineNetwork:
          cidr: 10.0.0.0/16
        serviceNetwork:
          - 172.30.0.0/16

      clusterInstall:
        createCluster: 'true'
        platform: aws
        baseDomain: {aws_base_domain}
        openshiftVersion: 'REPLACE_WITH_YOUR_OCP_VERSION'
        openshiftChannel: stable

        pullSecretRef:
          name: 'aws-creds'
          key: 'pullSecret'
          namespace: 'cluster-install-secrets'
        secretSourceNamespace: 'cluster-install-secrets'

      aws:
        region: {aws_region}
        credentialRef: 'aws-creds'
        sshPrivateKeyRef: 'aws-creds'
        sshKeyRef:
          name: 'aws-creds'
          key: 'ssh-publickey'
          namespace: 'cluster-install-secrets'
        fips: false
        networkType: OVNKubernetes

        controlPlane:
          replicas: 1
          instanceType: m5.2xlarge
          rootVolume:
            iops: 4000
            size: 100
            type: io1

        workers:
          replicas: 0
          instanceType: m5.xlarge
          rootVolume:
            iops: 2000
            size: 100
            type: io1
----

Field-by-field explanation:

`config.clusterSet: managed` is the most important line in this file. It is the only line that decides what kind of cluster `spoke-aws-1` will become. When this cluster joins the fleet as a `ManagedCluster`, the `cluster-set-assignment` policy stamps `cluster.open-cluster-management.io/clusterset=managed` onto it. The `cluster-labels` policy reads the `cluster-set.managed` ConfigMap and stamps every label defined in the `managed` clusterset's values file. Every Placement predicate that targets the `managed` clusterset matches this cluster. Everything Module 2 taught about the label flow applies to a cluster that does not exist yet.

`clusterInstall.createCluster: 'true'` is the provisioning trigger. Setting it to anything other than `'true'`, or removing it entirely, stops provisioning for that cluster.

`platform: aws` routes the install to the `policy-cluster-install-aws` policy chain, which creates a Hive `ClusterDeployment` rather than a SiteConfig `ClusterInstance`.

`openshiftVersion` sets the release the new cluster installs at, and it feeds the `ClusterImageSet` lookup. Replace `REPLACE_WITH_YOUR_OCP_VERSION` with the version you read from your own cluster a moment ago:

[source,role="execute"]
----
sed -i "s/REPLACE_WITH_YOUR_OCP_VERSION/${OCP_VERSION}/" \
  autoshift/values/clusters/spoke-aws-1.yaml
grep 'openshiftVersion' autoshift/values/clusters/spoke-aws-1.yaml
----

Installing the spoke at the same release as the hub keeps the lab simple. It is not a requirement: a fleet routinely runs mixed versions, and Module 9 covers how AutoShift moves clusters between them.

[NOTE]
====
Do not hardcode a version from a document into a values file, here or anywhere else in AutoShift.

`openshift-version` on a clusterset is the *desired* version. It drives operator-catalog alignment, and the `openshift-upgrade` policy treats it as an upgrade target: a cluster opted in to upgrades moves when its clusterset's `openshift-version` is higher than the cluster's current version. A number copied from a guide is a number nobody chose deliberately.

Note that `hub-minimal.yaml` ships with its own `openshift-version` value, which may be older than the cluster you are running. It is below your current version, so the upgrade policy takes no action, but it is worth knowing it is there rather than assuming it matches.
====

`pullSecretRef` uses the object form rather than a plain string name because the `aws-creds` secret stores the pull secret under the custom key `pullSecret`, not the default `.dockerconfigjson`. The policy reads the key by name via a hub template lookup.

`secretSourceNamespace: 'cluster-install-secrets'` tells the secrets policy where to find the source namespace on the hub. All 3 `*Ref` fields under `aws:` resolve from this namespace.

`aws.credentialRef: 'aws-creds'` points to the `aws_access_key_id` and `aws_secret_access_key` keys. Hive needs these to call AWS Identity and Access Management (IAM) APIs.

`aws.sshPrivateKeyRef: 'aws-creds'` points to the `ssh-privatekey` key. Hive embeds the private key in the `ClusterDeployment` so it can reach bootstrapped nodes.

`aws.sshKeyRef` reads `ssh-publickey` from the same secret. The public key goes into the install-config so nodes accept SSH connections from the installer.

`aws.controlPlane.replicas: 1` with `workers.replicas: 0` provisions single-node OpenShift (SNO). Those 2 values are the reason the block above does not look like the example file you copied, which defaults to 3 control-plane nodes and 3 workers. This is not just to save money.

A multi-availability-zone cluster creates 1 NAT gateway per zone, and each one consumes an Elastic IP. AWS sandbox accounts cap Elastic IPs, commonly at 5, and your hub cluster already holds several. Ask for a 3-zone spoke and the install fails partway through network creation:

----
api error AddressLimitExceeded: The maximum number of addresses has been reached.
----

That failure arrives after Hive has already created a virtual private cloud and subnets, so it looks like a networking bug rather than a quota. SNO provisions into a single zone with 1 NAT gateway and 1 Elastic IP, which is the smallest footprint a spoke can have.

[IMPORTANT]
====
SNO reduces the requirement to 1 Elastic IP. It does not create one out of nothing.

If your hub is itself a multi-zone cluster in the same sandbox account, it may already hold every Elastic IP the quota allows, in which case even a single-node spoke fails with the same `AddressLimitExceeded` error. Hive retries until `installAttemptsLimit` and then sets `ProvisionStopped`.

Check before you start. In the AWS console, open *EC2 -> Elastic IPs* and compare the count against your account's quota under *Service Quotas -> EC2 -> EC2-VPC Elastic IPs*. If there is no headroom, release an unused address or skip the provisioning exercises: modules 4 to 9 do not depend on them.

Stop a stuck provision cleanly by setting `createCluster: 'false'` and re-applying. Hive runs an uninstall job and releases whatever it did create.
====

Size the control plane accordingly: a single node runs the control plane and all workloads, so `m5.2xlarge` is the practical minimum.

`aws.fips: false` because this hub is not running in FIPS mode, and the installer refuses to build a FIPS cluster from a non-FIPS host. The ECDSA key you generated is what you would need if you set this to `true` on a FIPS-enabled hub.

The `controlPlane` and `workers` blocks set EC2 instance types and root volume sizes. These are the defaults from the example file.

=== Apply with the cluster values file

Add both new files as additional `-f` arguments: the managed clusterset the spoke will join, and the cluster itself. Most general file first, as always with Helm:

[source,role="execute"]
----
helm upgrade --install autoshift ./autoshift \
  -n openshift-gitops \
  -f autoshift/values/global.yaml \
  -f autoshift/values/clustersets/hub-minimal.yaml \
  -f autoshift/values/clustersets/managed-minimal.yaml \
  -f autoshift/values/clusters/spoke-aws-1.yaml
----

[IMPORTANT]
====
From here on, every `helm upgrade` must include all 4 values files.

Helm renders from exactly the files you pass. Drop `managed-minimal.yaml` or `spoke-aws-1.yaml` from a later command and AutoShift renders as though you never declared them: the `managed` clusterset and the `spoke-aws-1` rendered-config disappear, so the cluster stops being configured and stops being labelled.

That does not destroy anything. Removing a declaration removes AutoShift's management of the cluster, it does not deprovision it. An in-flight install keeps running to completion and an existing cluster keeps running unmanaged. You just lose the thread, and the fix is to pass all 4 files again. Module 10 covers what actually deprovisions a cluster.

The remaining modules show the shorter 2-file command, because each was written to stand alone. Keep appending your 2 extra `-f` arguments to every one of them.
====

ArgoCD reconciles the change. The `cluster-config-maps` policy creates the `spoke-aws-1.rendered-config` ConfigMap on the hub. The cluster-install policy chain begins.

== Troubleshooting

=== ClusterDeployment reports ProvisionStopped with InstallAttemptsLimitReached

Check the installer container rather than the `hive` container. The `hive` container only stages
binaries; the failure is in `installer`:

[source,role="execute"]
----
POD=$(oc get pods -n spoke-aws-1 --no-headers | awk '/provision/ {print $1}' | tail -1)
oc logs "$POD" -n spoke-aws-1 -c installer --tail=60 | grep -iE 'error|failed'
----

If you see `Failed to allocate Elastic IP` and `NatGatewaysReconciliationFailed`, the AWS account is
out of Elastic IPs. The default quota is 5 per region, and the hub cluster already consumes several
for its own NAT gateways, so a second cluster has none left. The installer reports this indirectly
as `infrastructure was not ready`, which does not mention addresses at all.

Confirm it:

[source,role="execute"]
----
aws ec2 describe-addresses --query 'length(Addresses)' --output text
aws service-quotas get-service-quota --service-code ec2 --quota-code L-0263D0A3 \
  --query 'Quota.Value' --output text
----

If those two numbers are equal, the account is at its limit. Release unused addresses, request a
quota increase, or run the spoke install in a region or account that is not already hosting the hub.
Hive retries up to `installAttemptsLimit` times and then stops, so nothing recovers on its own once
the limit is reached.

== Learning Outcomes

By completing this module, you should now understand:

* ✓ A registry and an entire OpenShift cluster are both declared the same way everything else in AutoShift is declared: labels in a values file, and a controller that reconciles toward them
* ✓ `odf-multi-cloud-gateway: standalone` brings up NooBaa without Ceph or dedicated storage nodes, which is what makes an in-cluster registry viable on a single lab cluster
* ✓ Enabling FIPS mode constrains the SSH key algorithm to ECDSA or RSA, because ed25519 is not FIPS-approved, and the resulting install failure is not obvious from the error
* ✓ The clusterset a cluster is assigned to determines everything it inherits, and that assignment can be declared before the cluster exists
* ✓ Declarative infrastructure means you describe the end state and reclaim your attention while controllers converge, which is why these 2 provisions run while you work through the next 6 modules
